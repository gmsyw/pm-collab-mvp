## 0. 概述

- **0.1 定位**：一套 **AI 与人类作为对等参与者**共同管理项目的软件系统，把 PM-AI 需求体系落地为可运行产品。人与 AI 使用同一份数据、同一套流程、同一套留痕。
- **0.2 核心命题**：
  1. **文件系统即消息总线**（承接通用方法原则②）：交接区目录 + 交接单 JSON 是人机/机机流转的统一通道；服务层监听交接区文件并入库；
  2. **流程引擎化**：8 阶段流水线与 4 个质量门禁由系统强制，人与 AI 都无法跳过；
  3. **卡点即人机接口**：人类只处理结构化卡点（搬运/决策/审批/签字），其余由 AI 侧自动完成。
- **0.3 命名**：暂定"人机共管（PM-Collab）"，待确认。

## 1. 设计目标与原则

### 1.1 目标

| 目标 | 说明 |
| --- | --- |
| 对等协作 | 人与 AI 是系统一等公民，同一数据模型、同一操作通道 |
| 流程强制 | 阶段不可跳过、门禁必须人类签字、测试不过不得验收 |
| 全程可审计 | 任一结论可回溯到 交互 + 证据 + 确认人 |
| 最小人类介入 | 人类只处理卡点，AI 承担扫描、派单、回收、归档、告警 |
| **网络部署与多人协作** | 支持局域网/网络部署，多用户并发操作（V0.2 新增） |
| 开箱即用 | 本机可单机部署，五库与交接区由软件托管 |

### 1.2 设计原则（承接需求书 1.6 与通用方法）

1. 对等双参与者；2. 流程引擎化；3. 文件即接口；4. 状态不入文件名、版本不覆盖；5. 追加式日志、证据链；6. 最小影响、权限隔离、定期备份；7. 引用不复制（规则以需求书为唯一权威，系统映射而非重抄）；8. **服务层 API 为唯一数据入口**（人类 UI、AI 通道均经服务层，AI 不直连数据库）。

## 2. 总体架构（分层）

```
交互层    人类侧（Web UI：看板/卡点队列/审批台/投喂回收助手） + AI 侧（文件协议/扫描触发/API 可选）
服务层    API（认证/RBAC · 流程引擎 · 任务引擎 · 交接总线 · 评审引擎 · 告警引擎 · 审计日志 · 报表）
          监听交接区文件 → 入库；对外提供 REST/WebSocket
领域服务  角色权限(L1-L4·名册·角色卡) · 文档五库 · 版本台账/基线 · 追加日志/证据链 · 人机对账 · 度量报表
数据层    结构化存储（PostgreSQL）+ 文件库（五库目录 · 交接区 · 版本库 archive）
AI 运行时 角色实例管理（PM-AI 等） · 外部评审桥接（可选）
```

## 4. 核心数据实体（12 类）

| 实体 | 关键字段（继承已评审文档） | 存储 |
| --- | --- | --- |
| 成员名册 | ID / 类型 / 姓名或实例 / 状态 / 汇报对象 | PG 表 |
| 角色卡 | ID / 类型 / 职责 / 负面清单 / 权限等级 / 数据与工具边界 / 汇报对象 / 降级预案 | PG 表 |
| 任务卡 | ID / 目标 / 输入 / 交付物及路径 / 验收标准 / 人-A / AI-R / 依赖 / 起止 / 优先级 / 状态 / 证据 / 完成摘要 | PG 表 + JSONB 扩展字段 |
| 交接单 | 编号 / 发起方 / 接收方 / 载体路径 / 状态（待投喂→已投喂→已回收→已闭环）/ 时间戳 / 关联任务 | PG 表（与交接区 JSON 文件双向同步） |
| 卡点信号 | 发生时间 / 触发者 / 内容 / 人类需要做什么 / 期望时限 / 关联任务（6 字段） | PG 表 |
| 文档条目 | 唯一编号 / 类型 / 名称 / 版本号 / 责任人 / 状态 / 存放路径 / 哈希 | PG 表（内容在文件库） |
| 评审意见 | 任务 / 评审人 / 级别（阻塞/建议/疑问）/ 意见 / 回复 / 状态 | PG 表 |
| 缺陷 | 编号 / 严重度 / 登记 / 回归结果 / 关闭标准 | PG 表 |
| 追加日志 | 时间 / 执行者 / 动作 / 产出物路径 / 变更 / 下一步 / 遗留问题 | PG 表（触发器 + REVOKE 强制只增） |
| 版本台账 | 版本号 / 日期 / 执行者 / 变更摘要 / 变更单 / 评审状态 / 路径 / 哈希 | PG 表（pgcrypto 校验） |
| 需求条目 | 编号 / 内容 / 评审状态 / 追溯链接 | PG 表 |
| 度量记录 | 周期 / 按期率 / 返工率 / AI 采纳率 / 评审关闭率 | PG 表 |

> 文件库（五库、交接区、archive）内容不进 PG；PG 仅存结构化记录与路径引用，保持"一次一处"。

## 5. 人机双通道设计

### 5.1 人类侧（界面）

| 视图 | 用途 |
| --- | --- |
| 项目看板 | 里程碑/任务/阶段总览，AI 自动更新 |
| 卡点待办队列 | 仅显示"人类需要做什么"，按清单执行即可 |
| 门禁审批台 | 4 门禁的签字/驳回入口 |
| 投喂/回收助手 | 拖拽文件即投喂目标对话、回收即归档（替代手工搬运） |
| 对账视图 | AI 完成项 vs 人工反馈，差异入台账 |

### 5.2 AI 侧（通道）

- **文件协议**：按约定读写交接区（派单/回执/完成/评审/卡点），格式统一；服务层监听入库；
- **扫描触发**：PM-AI 激活时按优先级扫描：任务状态→阻塞告警→门禁审批→版本归档→成员查询；
- **输出**：任务卡、完成摘要、评审证据包、告警、报表（AI 生成，系统留痕）。

### 5.3 同一份数据

AI 写交接区文件 → 服务层监听入库 → 人类看板实时可见；人类在界面操作 → 服务层落库 + 可选回写交接区文件 → AI 下次扫描即感知。**人与 AI 不直接互发指令，全部经服务层与交接区中转**（承接星型拓扑）。

## 6. AI 集成方式

| 方案 | 说明 | 建议 |
| --- | --- | --- |
| A 外部桥接（优先） | 各 AI 角色为独立对话/Agent（豆包、千问等），通过交接区文件 + 服务层投喂/回收自动化参与，对应通用方法星型拓扑 | **MVP 采用** |
| B 内置运行时 | 系统内嵌 LLM Agent 调度（PM-AI 等角色实例），经服务层 API 交互，无需人工投喂 | 演进方向（M3+） |

关键：无论 A/B，AI 的能力边界一致（角色卡权限），流程强制由引擎负责，AI 只做内容与判定辅助；**AI 一律不直连数据库**。

## 7. 部署与运行

- **部署形态**：服务层 + PostgreSQL + 文件库；可**本机单机部署**（本地 PG），亦可**网络部署**（局域网/公网，多用户经 Web UI 并发访问）。
- **数据库**：PostgreSQL（V0.2 决策）——MVCC 支撑多用户并发；JSONB 承接任务卡/交接单/卡点半结构化；RLS + RBAC 实现 L1–L4 权限隔离与多用户数据隔离；触发器 + 权限 REVOKE 在库层强制"追加式日志不可改删"；pgcrypto 提供版本台账哈希校验；物化视图支撑度量报表。
- **服务层**：REST/WebSocket API 为唯一数据入口；认证 + 会话管理；监听交接区文件自动入库。
- **目录托管**：软件自动维护 01-05 五库 + 交接区，不依赖人工建目录。
- **权限**：L1–L4 在服务层 + 数据库 RLS 双重强制；L3 需人类确认、L4 需备份+双人审批。
- **版本**：文件版本由系统管理（X.Y.Z、状态不入文件名、旧版保留）。
- **备份**：pg_dump 定时备份（结构化数据）+ 文件库快照（五库/交接区/archive），可一键恢复。
- **运行模式**：守护进程扫描交接区 + 定时报表；无 GUI 依赖，可纯文件驱动。

## 10. 技术选型（V0.3 新增）

### 10.1 选型总览

后端 **FastAPI（Python 3.12）** + **PostgreSQL 16** + 前端 **Vue 3**；AI 接入走"文件协议 + OpenAI 兼容 API"双通道，**不绑定任何 LLM 供应商**；本机到网络部署一条路径。

### 10.2 分层选型表

| 层 | 选型 | 关键理由 | 备选 |
| --- | --- | --- | --- |
| 后端框架 | FastAPI | 异步 + 原生 WebSocket（卡点队列实时）、自动 OpenAPI 文档、LLM/AI 生态主场 | NestJS、Go、ASP.NET Core |
| ORM/迁移 | SQLAlchemy 2.0 + Alembic | JSONB/RLS 支持成熟；迁移脚本即版本台账的代码侧 | Prisma、EF Core |
| 认证/权限 | JWT + RBAC（passlib/bcrypt） | 角色卡 L1–L4 映射为角色权限，库层 RLS 兜底 | OIDC（未来接企业 SSO） |
| 任务调度 | APScheduler | 每日摘要、扫描轮询、24h 告警检查；单进程够用 | Celery（M4+ 多机） |
| 文件监听 | watchdog | 交接区新文件 → 自动入库；卡点信号 → 通知 | asyncio 轮询（更简） |
| 前端 | Vue 3 + Vite + Element Plus | 管理型系统组件齐全、中文生态、与 ECharts 看板契合 | React + Ant Design |
| 实时通道 | WebSocket | 看板/卡点队列实时刷新 | SSE |
| AI 接入 | 文件协议（MVP）+ OpenAI 兼容 API（M3+） | 外部桥接不绑定 LLM SDK；内置运行时可用任一兼容端点 | LangGraph 编排（M3+） |
| 部署 | uv + 便携 PG（单机）→ Docker Compose（网络） | 本地零容器依赖；网络部署一条路径升级 | 裸机 systemd |
| 测试 | pytest + httpx（+ Testcontainers 集成测试） | 覆盖服务层与 PG 集成（RLS/触发器/JSONB） | — |

### 10.3 关键决策说明

1. **Python 而非 Node/Go/.NET**：AI 角色是本软件核心参与者（扫描、摘要、评审包、告警），Python 是 LLM/Agent 生态最短路径；团队已有 LangGraph + Docker + 远程 LLM 经验，技能复用。
2. **AI 中立设计**：MVP 阶段 AI 角色为"外部独立对话"，系统只认交接区文件——豆包、千问、Claude 等均可接入；内置运行时用 OpenAI 兼容协议，可随时切换供应商。
3. **单机到网络平滑演进**：本地开发 `uv + 便携版 PG`（零容器依赖）；M4 网络部署同一套代码用 Docker Compose 启动（nginx 反代 + HTTPS + 文件卷 + pg_dump 定时备份），无需重写。
4. **前端可替换**：前后端分离，Vue 3 为推荐非绑定；若团队更熟 React，接口不变。

### 10.4 部署演进与目录骨架

- 开发/单机：`uv` + venv + 便携版 PG（pg_ctl），零容器依赖；
- 网络（M4）：Docker Compose —— nginx(HTTPS) + FastAPI(uvicorn) + PostgreSQL 16 + 文件卷 + 备份 cron（pg_dump + 文件快照）；
- 代码骨架：

```
pm-collab/
├─ server/          # FastAPI 服务层（API · 流程引擎 · 交接总线 · 调度 · 监听）
├─ web/             # Vue 3 前端（看板 · 卡点队列 · 审批台）
├─ data/            # 数据目录（五库 + 交接区 + archive，软件托管）
└─ docker-compose.yml  # M4 网络部署编排
```

### 10.5 技术栈约束

- Windows 原生开发与运行（Python 全栈对 Windows 友好）；
- 不绑定任何云服务商与 LLM 供应商；本地优先，可平滑迁移。
